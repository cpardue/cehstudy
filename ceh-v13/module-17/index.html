CEH v13 Module 17: Mobile Platforms & IoT

This module covers security vulnerabilities in mobile platforms (Android, iOS) and IoT devices. Topics include jailbreaking/rooting, malicious applications, RFID/NFC cloning, Bluetooth attacks, smartwatch vulnerabilities, and IoT device exploitation.

Key Topics Covered

  • Android security: APK analysis, permission model, malware types
  • iOS jailbreaking and App Store sideloading risks
  • Mobile malware: trojans, spyware, ransomware, rootkits
  • RFID cloning and NFC skimming attacks
  • Bluetooth attacks: BlueBorne, bluesnarfing, bluejacking
  • IoT device vulnerabilities and firmware analysis
  • Mobile device lost/stolen procedures and data protection

Important Terms & Concepts

Jailbreaking (iOS): Removing manufacturer restrictions on iOS devices. Enables app sideloading but voids warranty, bypasses sandbox, and creates security risks.
Rooting (Android): Gaining elevated privileges on Android devices. Similar to jailbreaking — enables full system access but compromises security model.
RFID Cloning: Capturing and replicating RFID card data (access cards, payment cards). Low-frequency RFID (125 kHz) is easily cloned with inexpensive devices.
NFC Skimming: Using near-field communication readers to steal contactless payment or access card data. Requires close proximity but is harder to detect than RFID cloning.
BlueBorne: Critical Bluetooth vulnerability affecting Android and iOS. Allows takeover of devices through protocol stack exploits without pairing. Affects Bluetooth Classic and BLE.
Mobile Malware Vectors: Sideloading apps, SMS/phishing links (smishing), malicious QR codes (quishing), compromised third-party app stores, and drive-by downloads.

How to Study This Module

  • Differentiate Android vs iOS security models and attack vectors
  • Know RFID vs NFC vs Bluetooth attack types
  • Understand IoT device vulnerabilities: default credentials, unencrypted communications, outdated firmware

Frequently Asked Questions

What is the biggest mobile security threat?
Malicious apps (sideloading), phishing/smishing attacks, and unpatched OS vulnerabilities. For organizations: BYOD policies with proper MDM/MAM solutions.

How do you secure IoT devices?
Change default credentials, disable unnecessary services, keep firmware updated, segment on separate VLAN, and monitor for unusual network behavior.

What is Mobile and IoT Security in Ethical Hacking?

Mobile Platforms & IoT Security is a growing domain on the Certified Ethical Hacker v13 (CEH v13) exam administered by EC-Council. This module covers two interconnected attack surfaces: mobile devices (Android, iOS, tablets) and the broader Internet of Things (smart home devices, wearables, connected sensors). Mobile devices are increasingly used for corporate access (BYOD — Bring Your Own Device), making them high-value targets for data theft. IoT devices multiply the attack surface further — a single household may contain dozens of connected devices, many with no patching mechanism and weak authentication. On the CEH v13 exam, questions related to Module 17 account for approximately 6% of total questions.

Key Concepts in Mobile & IoT Security

  • Android Security Model & APK Attack Surface: Android's security model relies on: (1) Application sandboxing — each app runs in its own Linux UID with isolated data directories; (2) Permission system — apps must declare required permissions at install time, and the user can grant/deny them; (3) Code signing — APKs are signed with developer keys; (4) SELinux policy enforcement. Attack surface for CEH exam: Sideloading (installing unsigned or repackaged APKs from outside Play Store), permission escalation through vulnerable system services, inter-process communication (IPC) attacks via Intent hijacking, and APK decompilation (using apktool to examine code logic). On the CEH exam, know that Android is open-source (AOSP) while iOS is closed — this means Android vulnerabilities can be publicly analyzed and patched faster, but also that custom ROMs and rooted devices increase attack surface. Mobile malware on Android: banking trojans (FakeBank), spyware (SpyEye mobile), ransomware (locking device until payment), and SMS-forwarding malware that intercepts 2FA codes.
  • RFID vs NFC: Frequency, Range & Cloneability: RFID (Radio-Frequency Identification) operates at three frequency bands: Low Frequency (125-134 kHz, range ~10 cm), High Frequency (13.56 MHz, range ~1 meter — used in most access cards and contactless payment), and Ultra-High Frequency (860-960 MHz, range up to 12 meters — inventory/logistics). NFC (Near-Field Communication) is a subset of HF RFID operating at 13.56 MHz with range limited to ~4 cm — the short range is a security feature (prevents remote skimming). On the CEH exam, know that: LF RFID cards (125 kHz proximity badges like HID Prox) contain static IDs that are trivially cloned with $20 Proxmark devices; HF RFID/NFC payment cards use cryptographic authentication (EMV Contactless, ISO 14443) making cloning much harder but not impossible (Mifare Classic DESFire vulnerabilities); the primary attack vector for NFC payments is relay attacks (extending range between victim's card and terminal using two RFID readers) rather than direct cloning.
  • IoT Device Attack Patterns & Firmware Analysis: The most common IoT device vulnerabilities tested on CEH: (1) Default/weak credentials — many devices ship with admin/admin or no password, and users never change them; (2) Unencrypted administrative interfaces — HTTP (not HTTPS) for web panels, Telnet (not SSH) for command access; (3) Lack of patching mechanism — many IoT devices have no OTA update capability, leaving known CVEs exploitable indefinitely; (4) Insecure cloud connectivity — devices phoning home to vendor cloud with weak or no TLS; (5) Firmware backdoors — debug shells, hidden telnet interfaces, hardcoded API keys embedded in firmware. On the CEH exam, know that IoT device firmware analysis involves: extracting firmware from the device (JTAG/SWD for hardware, or downloading from vendor website), analyzing with binwalk (identifying and extracting filesystems), examining configuration files for hardcoded credentials, reviewing web application code for SQLi/XSS, and checking for debug interfaces. Mirai botnet is the most commonly referenced IoT attack — it exploits default credentials on IoT devices to build a DDoS botnet of 250,000+ compromised cameras and routers.
  • BlueBorne: Bluetooth Attack Without Pairing: BlueBorne (CVE-2017-0781 through CVE-2017-0949) is a critical Bluetooth vulnerability affecting Android, iOS, Windows, Linux, and BlackBerry that allowed unauthenticated attackers to hijack devices and spread via the air. Unlike most Bluetooth attacks that require prior pairing, BlueBorne exploited the Bluetooth protocol stack itself — specifically the SDP (Service Discovery Protocol), L2CAP (Logical Link Control and Adaptation Protocol), and ATT (Attribute Protocol) implementations. Attack capabilities: execute arbitrary code with full user privileges, access camera/microphone, steal Bluetooth-paired data, and spread worm-style to nearby devices. On the CEH exam, know that BlueBorne's criticality came from: (1) No pairing required — proximity is sufficient; (2) Affects all major OSes simultaneously; (3) Chainable — compromised device can infect others in range; (4) Exploit was public and reliable before most patches were deployed. Mitigation: patch the Bluetooth stack firmware, disable Bluetooth when not in use, and be aware of the ~10-meter effective range for Classic Bluetooth.

Tools Used in Mobile & IoT Hacking

Mobile and IoT security tools referenced on the CEH exam include Airspy (software-defined radio for intercepting and analyzing RF signals — used to identify RFID frequencies, clone low-frequency proximity cards, and perform passive surveillance of wireless device communications), Proxmark3 (the primary RFID/NFC attack tool: reads and writes LF/HF transponders, emulates card interactions, performs relay attacks, and can extract keys from Mifare Classic cards using nested authentication attacks), apktool (Android APK decompilation tool — disassembles smali bytecode and extracts resources for security analysis; used to identify hardcoded API keys, insecure data storage, and permission misconfigurations in Android apps), OWASP Mobile Security Testing Guide (MSTG) (free framework for mobile application penetration testing covering 50+ test cases across platform security, cryptography, data storage, and code quality), Ghidra (NSA open-source reverse engineering tool used to analyze IoT device firmware binaries — disassembles ARM/MIPS/PowerPC executables to find backdoors and hardcoded credentials), binwalk (firmware extraction tool that identifies embedded filesystems, archives, and images within firmware blobs), and Netcat/ncat (basic network tools for testing IoT device port exposure and manual service interaction). On the CEH exam, know that Proxmark3 is specifically associated with RFID/NFC attacks while Ghidra+binwalk are the standard pair for IoT firmware analysis.

How to Study Mobile & IoT Security for the CEH v13 Exam

To effectively study Module 17 for the Certified Ethical Hacker exam:

  1. Create a mobile platform comparison: Android vs iOS | Sandboxing mechanism | Permission model | Malware distribution channel | Root/Jailbreak method | Enterprise MDM support. The exam frequently asks which security feature belongs to which platform — e.g., "Which platform uses code signing to enforce app integrity?" (Answer: Both, but iOS enforces it more strictly; Android allows sideloading by default). Know that iOS is a closed ecosystem (all apps must be signed by Apple) while Android is open (users can install from any source)
  2. Hands-on exercise: Download a vulnerable Android app from a CTF platform and use apktool to decompile it. Identify: hardcoded API keys in strings.xml, insecure data storage in SharedPreferences, cleartext HTTP connections in network calls, and unnecessary permissions in AndroidManifest.xml. This mirrors exam questions about Android security assessment. For IoT: download a firmware image from a public dataset and use binwalk to extract the filesystem, then search for default credentials with grep
  3. Memorize the RFID frequency classification and cloneability: LF (125 kHz) — static ID, trivially cloned; HF (13.56 MHz) — cryptographic auth, harder to clone, NFC operates here; UHF (860-960 MHz) — long range, used for inventory not security. Know that Proxmark3 handles LF/HF while Airspy covers the broader RF spectrum including ZigBee (2.4 GHz) and sub-GHz IoT communications
  4. Review related modules: Module 16 (Wireless Networks) for the wireless attack techniques that apply to mobile devices (evil twin, deauth) since phones are wireless clients, and Module 18 (OT & IoT Attacks) for industrial control system attacks that extend beyond consumer IoT into SCADA/ICS environments — Module 17 covers consumer/smart device IoT while Module 18 covers critical infrastructure IoT

Frequently Asked Questions About Mobile & IoT Security

What is a Mifare Classic card and why is it vulnerable to cloning?

Mifare Classic (MIFARE 1K) is a 13.56 MHz HF RFID chip manufactured by NXP Semiconductors, widely used for access control cards, transit passes, and loyalty programs. Each card contains 4 KB of memory organized into 16 sectors, with each sector having its own encryption key (Key A and Key B) using the proprietary Crypto-1 cipher. The vulnerability: Crypto-1 was broken in 2008 by researchers at Radboud University Nijmegen, revealing that a known-answer attack requires only about 20,000 authentication attempts (achievable in minutes with Proxmark3). Additionally, the nested authentication flaw means that cracking Key A of one sector gives you Key B of that sector AND Key A of the next sector — cascading through all 16 sectors. On the CEH exam, know that Mifare Classic should never be used for high-security access control. Modern replacements include Mifare DESFire (AES-128 encryption) and iCLASS SE (3DES with anti-clone features). The practical attack: use Proxmark3 to read the UID (always in cleartext) and if needed, crack Crypto-1 keys to clone the full card state including access permissions.

How do you perform a firmware analysis on an IoT device for a CEH exam?

IoT firmware analysis workflow tested on the CEH exam: (1) Acquire firmware — download from vendor website, extract via serial console (UART), or dump from flash chip using JTAG/SWD hardware; (2) Identify format — use file command and binwalk to determine if firmware is compressed (gzip, lzma, squashfs) or raw flash layout; (3) Extract filesystems — binwalk -e firmware.bin recursively extracts all embedded archives and filesystems (often CramFS, JFFS2, UBI, or squashfs); (4) Analyze web interface code — examine CGI scripts and web application files for SQL injection, command injection, and path traversal vulnerabilities; (5) Search for credentials — grep -r 'password\|passwd\|admin' across all extracted files to find hardcoded default credentials, API keys, and cryptographic secrets; (6) Examine binaries — use Ghidra or IDA Pro to disassemble main executables, looking for debug interfaces (hidden telnetd, netcat backdoors), insecure random number generation, and buffer overflows; (7) Check for update mechanisms — identify if the device has an OTA update process and whether firmware is signed (if not signed, attacker can push malicious firmware); (8) Document findings with CVE references where applicable. On the CEH exam, know that the most commonly found vulnerabilities are: default credentials (admin/admin), unencrypted telnet interface, hardcoded encryption keys, and absence of any update mechanism.

The overlap: both involve insecure default credentials, lack of patching, and network segmentation failures. The difference: OT attacks target physical safety (manipulating process variables, stopping safety interlocks) while IoT attacks target data availability or financial gain. On the CEH exam, know that ICS/OT attacks carry higher severity because they can cause physical damage or loss of life
