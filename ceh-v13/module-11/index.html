CEH v13 Module 11: Session Hijacking

Session hijacking involves taking over an active user session by stealing or predicting the session token. This module covers TCP session hijacking, SIDJACKING, XSS-based attacks, cookie poisoning, session fixation, and prevention measures including HTTPS and secure cookie flags.

Key Topics Covered

  • TCP session hijacking: sequence prediction, IP spoofing, RST injection
  • SIDJACKING: stealing unencrypted session IDs over the network
  • XSS-based session hijacking: injecting JavaScript to steal cookies
  • Cookie poisoning and manipulation
  • Session fixation attacks
  • HTTP header manipulation techniques
  • Prevention: HTTPS, Secure/HttpOnly cookie flags, token binding

Important Terms & Concepts

TCP Session Hijacking: Attacker takes over an established TCP connection by predicting sequence numbers, spoofing the source IP, and injecting packets. Requires the attacker to be in-line with the traffic.
SIDJACKING: Stealing a user's session ID (cookie) from network traffic. Works when sessions use HTTP (not HTTPS). Tools: Wireshark, Firesheep.
XSS-Based Hijacking: Injecting malicious JavaScript into a vulnerable web page that reads the victim's cookies and sends them to the attacker. More common than SIDJACKING today.
Session Fixation: Attacker sets a known session ID for the victim, then waits for the victim to authenticate with that same ID. The attacker already knows the session token.
Cookie Poisoning: Tampering with session cookie data stored on the client side to manipulate application behavior or gain elevated privileges.

How to Study This Module

  • Understand the 4 steps of TCP session hijacking (sniff, sequence prediction, IP spoofing, RST injection)
  • Differentiate SIDJACKING from XSS-based cookie theft
  • Know prevention techniques: HTTPS, Secure/HttpOnly/SameSite flags, session regeneration after login

Frequently Asked Questions

What is session hijacking?
An attacker takes over an active user's session by stealing or predicting the session token, allowing unauthorized access without needing credentials.

How do you prevent session hijacking?
Use HTTPS for all sessions, set Secure and HttpOnly flags on cookies, regenerate session IDs after authentication, implement SameSite cookie attribute, and use multi-factor authentication.

What is Session Hijacking in Ethical Hacking?

Session Hijacking is a critical attack technique tested on the Certified Ethical Hacker v13 (CEH v13) exam administered by EC-Council. This module covers methods of taking over an authenticated user's session without needing their credentials — either by stealing the session token in transit (SIDJACKING), predicting TCP sequence numbers to inject packets into an active connection, or exploiting web vulnerabilities like XSS to exfiltrate cookies. The CEH v13 exam emphasizes that session hijacking is a direct threat to the Integrity pillar of the CIA triad because the attacker acts as the legitimate user — all actions appear authorized. On the CEH v13 exam, questions related to Module 11 account for approximately 10% of total questions.

Key Concepts in Session Hijacking

  • TCP Sequence Number Prediction: The foundational concept behind classic TCP session hijacking. TCP uses sequence numbers (SEQ) and acknowledgment numbers (ACK) to track packet ordering. An attacker who can observe enough traffic to determine the increment pattern of sequence numbers can predict the next expected value, then craft packets with correct SEQ/ACK values from a spoofed source IP. The target accepts these packets as legitimate because they appear to come from the expected address with correct sequencing. On the CEH exam, know that modern operating systems use random initial sequence numbers and entropy-based increments, making pure TCP hijacking extremely difficult against modern stacks — but it remains a heavily tested concept on the exam.
  • SIDJACKING vs XSS-Based Cookie Theft: Two distinct methods of stealing session identifiers. SIDJACKING: attacker is in-line with network traffic (same LAN or via ARP spoofing) and captures unencrypted HTTP cookies containing session IDs using a sniffer (Wireshark, Firesheep for WiFi). Requires the victim to be on unencrypted HTTP. XSS-Based: attacker exploits a Cross-Site Scripting vulnerability in the web application to inject JavaScript that reads document.cookie and exfiltrates it to an attacker-controlled server. Works even over HTTPS because the script executes within the victim's browser context. On the CEH exam, the key distinction is: SIDJACKING = network-level interception; XSS-based = application-level exploitation.
  • Session Fixation & Token Binding: Session fixation requires the attacker to plant or control the session ID BEFORE authentication. Methods include: URL parameter injection (?JSESSIONID=attacker_token), HTTP response header manipulation (Set-Cookie via proxy), or direct cookie planting. The fix is token regeneration upon login — the server issues a completely new random session ID after successful credential verification, invalidating any previously fixed token. Token binding (a newer standard) cryptographically binds the session token to specific TLS connection properties so stolen tokens cannot be replayed from a different connection. On the CEH exam, know that session fixation is less common in practice but a frequently tested concept because it tests understanding of when session IDs should change.
  • Defense in Depth for Session Security: The CEH exam tests layered session protections: (1) HTTPS everywhere (prevents SIDJACKING), (2) HttpOnly flag (prevents JavaScript from reading cookies — blocks XSS cookie theft), (3) Secure flag (cookie only sent over HTTPS), (4) SameSite attribute (prevents cross-origin cookie sending — mitigates CSRF-driven attacks), (5) Session timeout and IP binding, (6) MFA for sensitive actions (even if session is hijacked, additional verification required), (7) Anomaly detection (geographic impossibility, rapid location changes). On the exam, know that no single control is sufficient — defense in depth requires multiple layers.

Tools Used in Session Hijacking

Session hijacking tools referenced on the CEH exam include Firesheep (Firefox extension that captures unencrypted session cookies from HTTPS sites — demonstrates SIDJACKING on open WiFi networks; works by parsing HTTP Referer headers and Set-Cookie responses), Ettercap (powerful MITM framework supporting ARP poisoning, TCP stream editing, and session hijacking via its built-in filter system — can modify HTTP responses in real-time to inject session fixation payloads), Wireshark (packet analysis to observe TCP sequence patterns and identify unencrypted session tokens in plaintext traffic), tcpflow (extracts TCP streams for deeper analysis of session data), and Burp Suite (web proxy that can modify HTTP headers, intercept responses for session fixation testing, and detect missing Secure/HttpOnly flags). On the CEH exam, know that Ettercap is the most comprehensive single tool for demonstrating MITM-based session attacks in a lab, while Firesheep is specifically referenced for wireless SIDJACKING scenarios.

How to Study Session Hijacking for the CEH v13 Exam

To effectively study Module 11 for the Certified Ethical Hacker exam:

  1. Memorize the 4-step TCP hijacking process: (1) Sniff traffic to capture SEQ/ACK values, (2) Predict next sequence numbers based on observed increment pattern, (3) Send RST packet with spoofed source IP to kill victim's connection, (4) Inject new packets with correct SEQ/ACK from attacker IP — the exam may ask for the specific order or what each step accomplishes
  2. Create a comparison table: Attack Method | Required Position | Works Over HTTPS? | Primary Tool. This directly maps to exam questions asking you to identify which attack works under which conditions
  3. Hands-on exercise: In a VirtualBox lab with two VMs (attacker + target), use Ettercap to perform ARP poisoning between them, then use its filtering module to modify an HTTP response and inject a cookie. Observe in Wireshark how the modified packet appears on the wire — this demonstrates both SIDJACKING and session fixation in one exercise
  4. Review related modules: Module 14 (Web Application Hacking) for XSS vulnerability exploitation that enables cookie theft, and Module 8 (Sniffing & Traffic Analysis) for the traffic capture techniques that enable SIDJACKING

Frequently Asked Questions About Session Hijacking

Can session hijacking work over HTTPS?

Pure SIDJACKING (network-level cookie capture) cannot work over HTTPS because the session cookie is encrypted in transit — an on-path attacker sees only TLS-encrypted data. However, XSS-based session hijacking CAN work over HTTPS because the malicious JavaScript executes within the victim's browser context with full access to the application's data, regardless of transport encryption. The HttpOnly cookie flag prevents JavaScript from reading cookies (document.cookie returns empty for HttpOnly cookies), which specifically blocks the XSS-based vector. On the CEH exam, know that HTTPS prevents network-level interception but NOT application-level attacks — this is why HttpOnly is a critical complementary defense. The combination of HTTPS + HttpOnly + SameSite provides comprehensive session cookie protection against all common hijacking vectors.

What is the role of the SameSite cookie attribute in preventing session attacks?

The SameSite attribute (introduced by browsers in response to CSRF concerns) controls when cookies are sent with cross-origin requests. SameSite=Strict: cookie only sent for same-site requests (never on cross-origin). SameSite=Lax (browser default since 2020): cookie not sent on cross-site POST/PUT/DELETE but sent on cross-site GET for top-level navigations. SameSite=None: requires Secure flag, cookie always sent. On the CEH exam, understand that SameSite doesn't directly prevent session hijacking (the attacker still has a valid session token) but it prevents a related attack class: Cross-Site Request Forgery where an attacker's page makes requests to the victim's authenticated session. If cookies have SameSite=Strict, a cross-site attack page cannot trigger authenticated actions because the browser won't include the session cookie in cross-origin requests. The exam may ask you to match the SameSite value to its protection level.
