CEH v13 Module 15: SQL Injection

SQL injection (SQLi) is one of the most critical web application vulnerabilities. This module covers UNION-based, blind, boolean-based, and time-based SQL injection techniques. Learn how to use sqlmap for automated exploitation, bypass WAFs, and implement prevention through parameterized queries.

Key Topics Covered

  • SQL injection fundamentals and how it works at the query level
  • UNION-based SQL injection: combining results from multiple queries
  • Blind SQL injection: inferring data through true/false responses
  • Boolean-based blind SQLi: using HTTP response differences
  • Time-based blind SQLi: using SLEEP() and WAITFOR delays
  • Out-of-band SQL injection techniques
  • sqlmap tool usage and advanced options
  • WAF bypass techniques for SQL injection
  • Prevention: parameterized queries, prepared statements, input validation

Important Terms & Concepts

UNION-based SQLi: Uses the UNION operator to combine results from the original query with an attacker-injected SELECT statement. Requires same number of columns in both queries.
Blind SQL Injection: No data is returned in the response. Attacker infers data by observing true/false responses or time delays. Slower but works when error messages are disabled.
Boolean-based Blind SQLi: Injects conditions that evaluate to TRUE or FALSE, observing differences in HTTP response content to infer data character by character.
Time-based Blind SQLi: Uses database-specific time functions (SLEEP(5) in MySQL, WAITFOR DELAY '00:00:05' in MSSQL) to infer data based on response timing.
sqlmap: Open-source tool that automates SQL injection detection and exploitation. Supports UNION, blind, time-based, error-based, out-of-band techniques. Can take full database control.
WAF Bypass: Techniques to evade Web Application Firewalls: encoding (%27 for single quote), double encoding, comment injection (--, #), character set manipulation, and chunk size attacks.

How to Study This Module

  • Understand how SQL injection works at the query level (concatenation of user input into queries)
  • Differentiate UNION-based vs blind vs boolean-based vs time-based techniques
  • Know sqlmap command-line options for different attack scenarios
  • Memorize prevention: parameterized queries are the single most effective defense

Frequently Asked Questions

What is SQL injection?
Inserting malicious SQL code into input fields to manipulate backend database queries. Can lead to data theft, authentication bypass, and full database compromise.

What are the types of SQL injection attacks?
In-band (UNION-based, error-based), Blind (boolean-based, time-based), and Out-of-band. In-band is easiest — attacker uses same channel for attack and results. Blind is slower but works when errors are hidden.

What is SQL Injection in Ethical Hacking?

SQL Injection (SQLi) is the most critical and most commonly exploited web application vulnerability, representing a standalone module in the Certified Ethical Hacker v13 (CEH v13) exam administered by EC-Council. SQLi occurs when an application concatenates unsanitized user input into SQL queries, allowing an attacker to manipulate the query's logic and execute arbitrary database commands. Unlike other injection flaws that target operating systems or directory services, SQL injection targets the relational database engine itself — MySQL, Microsoft SQL Server, PostgreSQL, Oracle, SQLite. The impact ranges from unauthorized data access (reading all tables) to complete database compromise (modifying/deleting data, executing OS commands via xp_cmdshell on MSSQL). On the CEH v13 exam, questions related to Module 15 account for approximately 12% of total questions.

Key Concepts in SQL Injection

  • UNION-Based SQL Injection & Column Counting: UNION-based SQLi appends an attacker-controlled SELECT statement to the existing query using the UNION operator. The prerequisite: both queries must have the same number of columns. Attackers determine the column count by injecting ORDER BY n and incrementing n until an error occurs (e.g., ?id=1 ORDER BY 3 → error means fewer than 3 columns). Once the column count is known, the attacker injects NULL for non-displayed positions and data-extraction functions for displayed positions: ' UNION SELECT table_name,column_name,NULL FROM information_schema.columns--. On the CEH exam, know that UNION-based requires the application to display query results AND require the same column count. The information_schema database (MySQL) and sysobjects/syscolumns (MSSQL) are the metadata sources attackers query to enumerate table and column names before extracting actual data.
  • Blind SQLi: Boolean vs Time-Based Tradeoffs: Blind SQL injection is used when the application does not display query results or error messages. The attacker must infer data through side channels. Boolean-based: inject conditional logic (AND 1=1 / AND 1=2) and observe response differences — page length, element presence, HTTP status codes. One character extracted per request. Time-based: inject database sleep functions (SLEEP(5), WAITFOR DELAY '00:00:05', pg_sleep(5)) that only execute when a condition is true. The attacker measures response time to determine if the condition was satisfied. Time-based is 10-50x slower than boolean-based but works even when responses are identical regardless of query result. On the CEH exam, the key distinction: boolean-based requires observable response differences (any difference works — even a single pixel); time-based works when NO observable difference exists. Both extract data one character at a time using SUBSTRING() or LEFT() functions.
  • Out-of-Band SQLi & Stacked Queries: Out-of-band (OOB) SQL injection exfiltrates data through a channel other than HTTP — typically DNS or HTTP callbacks. The attacker uses database functions to make outbound connections: MSSQL's xp_cmdshell + certutil for HTTP, MySQL's LOAD_FILE() for local file read, PostgreSQL's COPY TO PROGRAM for OS command execution, Oracle's UTL_HTTP.request() for HTTP callbacks. OOB SQLi works when the database server has internet access but the application returns no useful response data. Stacked queries (also called multi-statement injection) allow executing multiple SQL commands in a single input by separating them with semicolons: ' DROP TABLE users; --. Not all databases support stacked queries — MySQL does, MSSQL does, PostgreSQL does NOT (single-statement only), Oracle does via PL/SQL blocks. On the CEH exam, know that OOB is the fallback when both blind techniques are too slow or blocked, and that it requires the database server to have outbound network access.
  • Parameterized Queries as Primary Prevention: The single most effective SQLi prevention: parameterized queries (prepared statements). Instead of concatenating user input into SQL strings, the query structure is sent to the database first (the prepared statement), and user input is sent separately as data parameters. The database engine treats parameters strictly as data, never as executable SQL code — regardless of what characters they contain. Example: Instead of "SELECT * FROM users WHERE username='" + userInput + "'", use "SELECT * FROM users WHERE username = ?" with userInput passed as a bound parameter. On the CEH exam, know that input validation (blacklisting SQL metacharacters) is NOT sufficient as a standalone defense — it can be bypassed with encoding, comments, and alternative syntax. Parameterized queries work because they separate code from data at the protocol level, making bypass impossible regardless of input content.

Tools Used in SQL Injection

SQL injection tools referenced on the CEH exam include sqlmap (the industry-standard automated SQLi detection and exploitation tool; key commands: sqlmap -u "http://target/page?id=1" --dbs enumerates databases, --tables enumerates tables in a database, --dump dumps table contents, --technique=BEUSTQ selects specific injection techniques, --batch runs without interactive prompts, --proxy="http://127.0.0.1:8080" for Burp integration), Burp Suite (web proxy that intercepts requests to test SQLi manually by injecting single quotes, UNION SELECT statements, and conditional time delays into parameters; the Repeater tool is essential for iterating blind SQLi payloads), OWASP ZAP (free alternative with automated SQLi scanning as part of its active scan), Nmap NSE scripts (vuln detection: mysql-empty-password, mysql-enum — identify MySQL versions and weak configurations before attempting injection), and DVWA/SQLi labs (deliberately vulnerable practice environments for hands-on SQLi exploitation). On the CEH exam, sqlmap is the most frequently referenced tool — know that it automates all major injection types and can be configured to use specific techniques when others fail.

How to Study SQL Injection for the CEH v13 Exam

To effectively study Module 15 for the Certified Ethical Hacker exam:

  1. Memorize the SQLi classification hierarchy: In-band (UNION-based, Error-based) → data returned in same channel; Blind (Boolean, Time-based) → data inferred from response differences or timing; Out-of-Band → data exfiltrated via DNS/HTTP callbacks. The exam asks you to classify attack scenarios into these categories and identify which technique is appropriate given the constraints (e.g., "errors are suppressed, but responses differ" = boolean-based blind)
  2. Hands-on exercise: Set up DVWA (Damn Vulnerable Web Application) with a local MySQL database. Practice all injection types: error-based (injecting invalid SQL to force error messages revealing table structure), UNION-based (counting columns, using information_schema), and boolean blind (iterating character by character). For each, document the exact payload, what the response reveals, and which sqlmap command would automate it. This directly maps to exam questions that present a scenario and ask for the appropriate technique
  3. Memorize database-specific functions: MySQL — SLEEP(), BENCHMARK(), information_schema, LOAD_FILE(), INTO OUTFILE; MSSQL — WAITFOR DELAY, sysobjects, xp_cmdshell, OPENROWSET; PostgreSQL — pg_sleep(), information_schema, COPY TO PROGRAM; Oracle — UTL_HTTP.request(), all_tab_columns. The exam may name a specific database and ask which function to use for time-based blind or data exfiltration
  4. Review related modules: Module 14 (Web Application Hacking) for the OWASP A03 (Injection) framework context and how SQLi fits into broader web application attack chains, and Module 13 (Web Server Hacking) for how server-level misconfigurations (verbose error pages, unnecessary database access permissions) increase SQLi attack success

Frequently Asked Questions About SQL Injection

How do you identify a potentially vulnerable parameter for SQL injection?

Several indicators suggest a parameter may be vulnerable to SQL injection: (1) Single quote test — append a single quote (') to the parameter value. If the application returns an error message referencing SQL syntax, a database query, or "unterminated string literal", the input is being concatenated into SQL without sanitization; (2) Boolean test — append ' AND 1=1 vs ' AND 1=2. If responses differ (different page length, different content), the parameter affects query logic; (3) Time-based test — append ' AND SLEEP(5)-- or '; WAITFOR DELAY '00:00:05'--. If response takes ~5 seconds longer, SQLi is confirmed even without visible errors; (4) URL encoding — if the error disappears with %27 (URL-encoded quote) but reappears when decoded server-side, input is being processed in SQL context; (5) Parameter position — numeric parameters that should be integers (e.g., ?id=1) are more commonly vulnerable because developers often skip type validation. On the CEH exam, know that a single prime test is the fastest initial check, but confirmation requires demonstrating actual data manipulation or authentication bypass — not just an error message.

What WAF bypass techniques work against SQL injection filters?

Common WAF bypass techniques for SQL injection filters include: (1) URL encoding — encode the single quote as %27, or double-encode as %2527 if the WAF only decodes once; (2) Inline comments — use MySQL comment syntax /*!...*/ to break up keywords: UN/**/ION SEL/**/ECT (the WAF doesn't see the full keyword); (3) Case variation — some WAFs are case-sensitive: SeLeCt, UnIoN, sLeEp(); (4) Alternative syntax — use information_schema instead of SHOW TABLES, use 0x41 (hex) instead of 'A' for string comparison; (5) Chunked transfer encoding — split the payload across multiple HTTP chunks so no single chunk contains the full attack pattern; (6) HTTP parameter pollution — duplicate the parameter (?id=1&id=1 UNION SELECT...) to confuse WAF parsing while the application uses one value; (7) Character set manipulation — use GBK/UTF-8 multi-byte characters where a trailing byte can escape a string context. On the CEH exam, know that no single bypass technique guarantees success — effective bypass requires understanding the specific WAF's rule set and encoding behavior. The most reliable defense against SQLi remains parameterized queries, which make all WAF bypass techniques irrelevant.
