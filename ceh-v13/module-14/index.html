CEH v13 Module 14: Hacking Web Applications

This module covers attacks against web applications, focusing on the OWASP Top 10 vulnerabilities. Attackers exploit XSS (reflected, stored, DOM-based), CSRF, injection flaws, security misconfigurations, and broken authentication to compromise web application systems and data.

Key Topics Covered

  • OWASP Top 10 categories and their evolution in v13
  • Reflected XSS vs Stored XSS vs DOM-based XSS
  • Cross-Site Request Forgery (CSRF) attacks and token bypass
  • SQL injection, command injection, LDAP injection
  • Security misconfiguration: default credentials, verbose errors
  • Broken authentication and session management
  • Insecure Direct Object References (IDOR)

Important Terms & Concepts

OWASP Top 10: The ten most critical web application security risks, updated periodically. Categories include injection, broken authentication, XSS, insecure direct object references, security misconfiguration, and more.
Reflected XSS: Malicious script is embedded in a URL or form submission and executed immediately in the victim's browser. Not stored on the server. Requires tricking user into clicking a crafted link.
Stored XSS: Malicious script is permanently stored on the target server (in comments, user profiles, forums). Every user who views the stored data is affected — most dangerous XSS type.
DOM-based XSS: Vulnerability exists in client-side JavaScript rather than server code. The attack modifies the DOM environment in the victim's browser without server interaction.
CSRF (Cross-Site Request Forgery): Forces an authenticated user's browser to perform unwanted actions on a trusted site. Mitigated with anti-CSRF tokens, SameSite cookies, and re-authentication for sensitive operations.
IDOR (Insecure Direct Object References): Accessing resources by manipulating object identifiers in URLs (e.g., changing ?user_id=100 to ?user_id=101). Allows unauthorized access to other users' data.

How to Study This Module

  • Know all OWASP Top 10 categories and their descriptions
  • Differentiate reflected vs stored vs DOM-based XSS with examples
  • Understand CSRF attack flow and mitigation techniques
  • Practice identifying web application vulnerabilities in sample code

Frequently Asked Questions

What is the OWASP Top 10?
A standard awareness document for web application security listing the ten most critical security risks. It is updated every few years to reflect evolving threats.

What are the types of XSS attacks?
Three types: Reflected (script delivered via link), Stored (script saved on server), and DOM-based (exploits client-side JavaScript). Stored XSS is most dangerous as it affects all visitors.

What is Web Application Hacking in Ethical Hacking?

Web Application Hacking is the highest-weighted web security domain on the Certified Ethical Hacker v13 (CEH v13) exam administered by EC-Council. This module focuses on vulnerabilities in the application layer — the code, inputs, sessions, and business logic that run on top of web servers (covered in Module 13). The CEH v13 exam organizes these attacks around the OWASP Top 10 framework, which represents the most commonly exploited web application vulnerabilities in production systems. Web applications are the primary interface between users and organizational data, making them the most frequently targeted attack surface in modern enterprise environments. On the CEH v13 exam, questions related to Module 14 account for approximately 15% of total questions.

Key Concepts in Hacking Web Applications

  • XSS Vulnerability Classifications (Reflected vs Stored vs DOM-based): Cross-Site Scripting injects malicious JavaScript into web pages viewed by other users. The three types differ in persistence and attack complexity. Reflected (non-persistent): payload lives only in the request — attacker crafts a URL containing the script, victim clicks it, server reflects it back. Stored (persistent): payload is saved in the application's database — every visitor gets infected automatically without any social engineering. DOM-based: the vulnerability exists entirely in client-side JavaScript that unsafely uses user-controllable data (document.location.hash, window.name, document.referrer) to modify the page DOM without any server round-trip. On the CEH exam, the most frequently tested distinction is reflected vs stored — know that stored XSS is more dangerous because it's self-propagating, while reflected XSS requires victim interaction (clicking a link). The HttpOnly cookie flag specifically blocks both reflected and stored XSS from exfiltrating session cookies via document.cookie.
  • CSRF Attack Flow & Mitigation Stack: Cross-Site Request Forgery exploits the fact that browsers automatically include cookies with cross-origin requests. The attack flow: (1) Attacker hosts a page with hidden form or JavaScript that sends a request to the target site, (2) Victim visits the attacker's page while authenticated to the target, (3) Browser automatically includes the victim's session cookie in the request to the target, (4) Target processes the request as if the victim initiated it — state change occurs (password change, fund transfer, permission grant). The mitigation stack: (1) Anti-CSRF tokens — unique per-session values that must be included in forms (attacker can't read them due to Same-Origin Policy), (2) SameSite cookie attribute — browser won't send cookies on cross-origin requests, (3) Verify Origin/Referer headers server-side, (4) Re-authentication for sensitive operations. On the CEH exam, know that CSRF does NOT give the attacker access to data (Same-Origin Policy prevents reading responses) but CAN force state changes — the distinction between read and write access is commonly tested.
  • IDOR & Broken Access Control: Insecure Direct Object References occur when an application exposes an object identifier (database ID, filename, URL parameter) without verifying that the requesting user has permission to access that specific object. Example: /api/orders?order_id=1002 returns order details for any user who guesses or increments the ID. On the CEH exam, know that IDOR is now classified under OWASP A01:2021 (Broken Access Control) — the 2021 Top 10 consolidated several older categories. The defense is server-side authorization checks on every object access, not just authentication. Indirect references (using UUIDs or hashed identifiers instead of sequential integers) reduce the risk but are not a complete fix — the server must still verify the requesting user owns that resource.
  • OWASP Top 10 Evolution (2017 → 2021): The CEH v13 exam references the OWASP Top 10 framework. Key changes from 2017 to 2021: Insecure Direct Object References (A05:2017) was merged into Broken Access Control (A01:2021); Security Misconfiguration (A05:2017) became Vulnerable and Outdated Components (A06:2021); Server-Side Request Forgery (SSRF) was promoted from the 2013 list back to Top 10 as A10:2021. The current 2021 list: A01 Broken Access Control, A02 Cryptographic Failures, A03 Injection, A04 Insecure Design, A05 Security Misconfiguration, A06 Vulnerable and Outdated Components, A07 Identification and Authentication Failures, A08 Software and Data Integrity Failures, A09 Security Logging and Monitoring Failures, A10 SSRF. On the CEH exam, know the category names and which specific attacks fall under each — e.g., SQL injection falls under A03 (Injection), weak TLS configuration falls under A02 (Cryptographic Failures).

Tools Used in Web Application Hacking

Web application attack tools referenced on the CEH exam include Burp Suite (the industry-standard web application proxy for intercepting, modifying, and replaying HTTP requests; used to test XSS by injecting payloads into parameters, test CSRF by removing anti-CSRF tokens, enumerate IDOR by incrementing object IDs, and run automated vulnerability scans with the Pro scanner), OWASP ZAP (Zed Attack Proxy) (open-source alternative to Burp Suite with automated active and passive scanning; the CEH exam references it as a free tool for web application security testing), SQLMap (automated SQL injection detection and exploitation tool that tests all input parameters for SQLi using multiple techniques — union-based, boolean blind, time-based, error-based, and out-of-band), Wapiti (command-line web application scanner detecting XSS, SQLi, command injection, and path traversal vulnerabilities), and OWASP WebGoat (deliberately vulnerable training application maintained by OWASP that demonstrates all Top 10 vulnerabilities in an interactive lab environment — ideal for hands-on practice before the CEH exam). On the CEH exam, know that Burp Suite is the most commonly referenced tool for manual web application testing, while SQLMap is specifically associated with SQL injection exploitation.

  3. Memorize XSS payload structures for each type: Reflected = '' in URL parameter; Stored = same payload in a comment/profile field; DOM-based = vulnerable JavaScript like document.write(location.hash). Know which HttpOnly/Content-Security-Policy/SameSite flags block which XSS vector
  4. Frequently Asked Questions About Web Application Hacking

What is Content-Security-Policy (CSP) and how does it prevent XSS?

Content-Security-Policy is an HTTP response header that tells the browser which sources of content are allowed to execute. A strict CSP (e.g., "default-src 'self'") means only scripts from the same origin can run — any injected inline script or external script from an attacker's domain is blocked by the browser before execution. On the CEH exam, understand how CSP complements other XSS defenses: HttpOnly blocks cookie theft but doesn't prevent the XSS itself (the script still executes for DOM manipulation, data exfiltration via API calls, etc.); CSP blocks the malicious script from executing in the first place. The most effective defense combines both: CSP prevents execution, HttpOnly limits the damage if XSS occurs anyway. A common CSP bypass technique tested on advanced exams: if the policy allows 'unsafe-inline', attackers can still inject inline scripts — so the strongest CSP omits 'unsafe-inline' and uses nonces or hashes instead. The CEH v13 exam may present a CSP header and ask whether a specific attack would be blocked by it.

How does SQL injection differ from other injection flaws in the OWASP Top 10?

All injection flaws share the same root cause: the application concatenates user input into a command (SQL query, OS command, LDAP query, XML document) without proper sanitization or parameterization. The difference is the target language and the resulting impact. SQL Injection (most common): user input is concatenated into SQL queries — attacker can read/modify/delete database contents, authenticate as any user, or in some DBMS configurations execute OS commands. OS Command Injection: user input is passed to system() or exec() calls — attacker executes arbitrary shell commands on the server. LDAP Injection: user input is inserted into LDAP directory queries — attacker can enumerate directory users, bypass authentication, or modify attributes. XML Injection (XXE): user input is processed as XML — attacker can read local files, perform SSRF, or trigger denial of service. On the CEH exam, all four fall under OWASP A03:2021 (Injection). The universal defense for all types is input validation and parameterized queries (prepared statements for SQL, escaped arguments for OS commands, proper XML parsers with external entity loading disabled for XXE). The exam may present code snippets and ask you to identify which injection type is present.
