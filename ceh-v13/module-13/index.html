CEH v13 Module 13: Hacking Web Servers

This module covers attacks against web server platforms including IIS, Apache, and nginx. Attackers exploit misconfigurations, directory traversal vulnerabilities, default credentials, unnecessary modules, and HTTP method abuses to gain unauthorized access to web server systems.

Key Topics Covered

  • IIS vulnerabilities: IIS 6.0/7.0 path parsing, ASP.NET attacks
  • Apache exploits: .htaccess manipulation, mod_ssl vulnerabilities
  • Web server misconfigurations and hardening techniques
  • Directory traversal attacks (../, URL encoding)
  • HTTP methods: TRACE, TRACK, PUT, DELETE exploitation
  • Default credentials and unpatched services
  • Unnecessary modules and attack surface reduction

Important Terms & Concepts

IIS (Internet Information Services): Microsoft's web server for Windows. Vulnerabilities include path parsing in IIS 6.0 (.asp; extension), ASP.NET view state exploitation, and default configuration weaknesses.
Apache Exploits: Includes .htaccess manipulation to execute PHP, mod_ssl heartbleed-like vulnerabilities, directory listing enabled by default, and misconfigured virtual hosts exposing sensitive files.
Directory Traversal: Using ../ sequences (or URL-encoded variants like %2e%2e%2f) to access files outside the web root. Can expose /etc/passwd, configuration files, and source code.
HTTP TRACE Method: Echoes back the request content — used in Cross-Site Tracing (XST) attacks to steal cookies or credentials. Should be disabled on production servers.
Nginx Misconfigurations: Includes improper fastcgi configuration, directory listing, default virtual host settings, and worker process privilege issues.

How to Study This Module

  • Know common vulnerabilities for IIS, Apache, and nginx specifically
  • Understand directory traversal techniques and URL encoding bypasses
  • Memorize which HTTP methods should be enabled/disabled on production servers

Frequently Asked Questions

What are common web server vulnerabilities?
Misconfigurations (directory listing, default pages), outdated software versions, unnecessary modules, weak file permissions, enabled dangerous HTTP methods, and default credentials.

How do you secure IIS and Apache?
Apply security patches, disable unnecessary modules/methods, configure proper file permissions, disable directory listing, remove default pages, and implement web server hardening guidelines.

What is Web Server Hacking in Ethical Hacking?

Web Server Hacking is a critical domain tested on the Certified Ethical Hacker v13 (CEH v13) exam administered by EC-Council. This module covers attacks against the web server platforms themselves — IIS, Apache HTTP Server, and nginx — rather than the applications running on top of them. Unlike Module 14 which focuses on application-level vulnerabilities (XSS, SQLi), Module 13 targets the server's own misconfigurations, parsing bugs, and protocol weaknesses. Web servers are the gateway to most internet-facing systems, making their compromise a high-priority attack objective. On the CEH v13 exam, questions related to Module 13 account for approximately 10% of total questions.

Key Concepts in Hacking Web Servers

  • IIS Path Parsing Vulnerability (.asp;.txt): In IIS 6.0, the server processes files from left to right, checking extensions against registered handlers. If an attacker names a file "evil.asp;.jpg", IIS 6.0 sees ".asp" first and executes it as ASP code, while the browser sends it as an image request. This bypasses upload restrictions that only block .asp/.aspx extensions. IIS 7.0 changed to right-to-left parsing, closing this specific vector. On the CEH exam, know that path parsing bugs are version-specific — the exam may ask which IIS version is vulnerable to which parsing order. The practical implication: never trust file extension filtering as your sole defense against script execution.
  • Directory Traversal & URL Encoding Bypasses: Directory traversal uses "../" sequences to navigate outside the web document root and access arbitrary files on the server. Basic traversal: /page?file=../../../etc/passwd. When the server blocks literal "../", attackers use encoding bypasses: %2e%2e%2f (URL-encoded), ..%c0%af (UTF-8 overlong), ..%252e%252f (double URL encoding), or backslash variants (..\..\). The CEH exam tests whether you can identify which encoding variant defeats which filter. On the exam, know that proper defense requires server-side input validation that decodes and normalizes the path before file access — not just pattern-matching against raw input strings.
  • HTTP TRACE Method & XST Attacks: The HTTP TRACE method echoes back the client's request exactly as received by the server, including headers. In a Cross-Site Tracing (XST) attack, an attacker hosts a JavaScript page that sends a cross-origin TRACE request to the victim's authenticated session. The server's response includes the Set-Cookie header containing the session token. Without SameSite cookie protection or CORS restrictions, the JavaScript can read this echoed response and exfiltrate the session ID. On the CEH exam, know that TRACE should be disabled on all production web servers (configured via in IIS or Limit in Apache). The XST attack is specifically referenced in OWASP as a lesser-known but valid cookie theft vector.
  • Web Server Hardening & Attack Surface Reduction: Defense strategy: (1) Remove all unnecessary modules and handlers — every loaded module is potential attack surface, (2) Disable dangerous HTTP methods (TRACE, PUT, DELETE, OPTIONS) on production servers, (3) Remove default pages and test files (default.php, server-status), (4) Configure proper file permissions so the web server user cannot read system files, (5) Disable directory listing (Options -Indexes in Apache, Directory Browsing in IIS), (6) Use a Web Application Firewall (WAF) as defense-in-depth, (7) Keep the server OS and web platform patched. On the CEH exam, know that hardening is an ongoing process — new vulnerabilities are discovered regularly in even well-maintained platforms like Apache 2.4.x.

Tools Used in Web Server Hacking

Web server attack tools referenced on the CEH exam include Nmap + NSE scripts (vuln detection: http-put, http-trace, http-methods scripts test for dangerous method exposure; http-apache-negotiation-check tests mod_negotiation misconfigurations), Metasploit (web server-specific exploits: multiple iis_webserver vulnerabilities, apache mod_cgi exploits, nginx off-by-one overflow), Burp Suite (proxy that intercepts HTTP requests to test directory traversal by modifying path parameters, test dangerous methods via Repeater, and identify information disclosure in response headers like Server and X-Powered-By), DirBuster/DirSearch (directory brute-forcing tools that find hidden paths, backup files, and administrative interfaces not listed in navigation — e.g., /admin/, /backup/, /config.php.bak), and Wapiti (web application scanner specifically designed to detect server-level issues like directory traversal, CORS misconfiguration, and HTTP method exposure). On the CEH exam, know that DirBuster is the most commonly referenced tool for finding hidden web server paths during reconnaissance.

Frequently Asked Questions About Web Server Hacking

How do you determine which web server a target is running?

Several techniques reveal the web server platform during reconnaissance: (1) HTTP response headers — the Server header often reveals the platform and version (e.g., "Server: Microsoft-IIS/7.5", "Server: Apache/2.4.41 (Ubuntu)", "Server: nginx/1.18.0"), though many administrators suppress this via hardening; (2) Error pages — unhandled errors often display server-specific error pages with version information (IIS blue screen, Apache error page, nginx 50x page); (3) File extensions in URLs — .asp/.aspx indicate IIS with ASP.NET, .php suggests Apache or nginx with PHP-FPM, .do/.action suggest Java application servers; (4) Default paths — /iissamples/ indicates IIS, /server-status indicates Apache, /nginx_status indicates nginx; (5) Nmap version detection (-sV flag) and NSE scripts specifically designed for web server fingerprinting. On the CEH exam, know that header analysis is the fastest method but unreliable if the administrator has hardened the server — error page analysis is the fallback when headers are suppressed.

Why are unnecessary web server modules a security risk?

Each loaded web server module increases the attack surface — more code running in the server's memory means more potential vulnerabilities to exploit. Examples: Apache's mod_php loads PHP as a library within Apache (vs PHP-FPM which runs it separately) — a PHP memory corruption bug can crash or compromise Apache itself. Apache's mod_negotiation enables content negotiation based on client Accept headers — misconfigured, it allows directory listing and file access via partial filename matching. IIS's ASP.NET handlers process all .aspx requests — if the application has an insecure ViewState configuration, an attacker can forge server authentication state. The principle: if your application doesn't use a module, disable it. On the CEH exam, know that the OWASP Top 10 references "Security Misconfiguration" (A05) which specifically includes running with default settings and unnecessary modules enabled. The defense is to maintain a documented baseline of required modules and periodically audit the running configuration against it.
